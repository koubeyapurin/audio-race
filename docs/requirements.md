# 声で地形を作るレースゲーム 要件定義書

- 仮称：**Voice Terrain Runner（ボイス・テレイン・ランナー）**
- バージョン：v1.0（共同開発練習用MVP）
- 作成日：2026-10-09
- 対象：大学生2名による共同開発練習
- ステータス：**開発の初期合意用。実装詳細・役割分担はClaude Codeによる計画提案を受けて確定**

## 1. 背景・目的

本プロジェクトは、声の高さ・大きさ・リズムで地形が変化する、ブラウザで遊べる横スクロール型レースゲームを作る練習プロジェクトである。

### プロダクトの目的
プレイヤーが声を使って自分の走るコースを生成・変形させる、新しい操作体験を提供する。

### 開発練習の目的
1. Windows PC 2台で、Git/GitHubを使う2人の共同開発を経験する。
2. Claude Code、Codex、Herdrを各自が必要に応じて使い、AI駆動開発の進め方を試す。
3. 動くゲームを最後まで完成・統合・テスト・公開する。
4. 問題発生時にログを確認し、AIと協力して原因を切り分けられるようにする。

**JPHACKS本番への提出作品はまだ未決定。これは共同開発の練習であり、JPHACKS本番作品と同一視しない。**

## 2. ゲーム概要

### 2.1 コンセプト
**「声で道をつくり、ゴールまで走れ！」**

プレイヤーは自動で右方向に進むランナーを操作する。ただし、左右移動を直接操作するのではなく、マイクに向かって声を出すことで、**ランナーの少し先に生成される地面の形を変える**。

声の高さで上り坂・下り坂の方向を、大きさで変化の強さを、声のリズムで小さな波・起伏を作る。地面の高度を調整して「音符（収集アイテム）」を集め、「障害物」を避けながらゴールを目指す。

### 2.2 想定プレイヤー・プレイ時間
- 対象：PCのマイクを使用できる人、またはキーボードで試したい人
- 人数：**1人プレイ**（※開発者が2人であることと、2人対戦ゲームであることは別）
- 形式：2D横スクロール／タイムトライアル風／1ステージ
- 1プレイ：約60秒（調整可能）
- 推奨環境：Windows 11 の最新ChromeまたはEdge、1280×720程度の画面

### 2.3 基本ループ
1. タイトル画面で「マイク操作」または「キーボード操作」を選ぶ。
2. マイクの場合は利用許可を求め、入力レベルを確認する。
3. カウントダウン後、キャラクターが右へ自動で走る。
4. 画面右側の**これからできる地面**を声で変化させ、収集アイテムを取る／障害物を回避する。
5. ゴールまたはゲームオーバーでスコアを表示し、再挑戦できる。

## 3. ゲーム仕様（MVP）

### 3.1 地形生成とランナー
- 地面は2Dの連続した曲線（または曲線を近似する折れ線）として表示し、その下側を塗りつぶす。
- ランナーは固定速度で画面の右方向に自動走行する。カメラがランナーを追従する。
- 地形はランナーの**約1〜2秒先**に向けて少しずつ生成し、すでに生成された部分は原則として固定する。
- ランナーはその時点の地面の高さに沿って移動する（実際の剛体物理演算は必須ではない）。
- 地形の勾配・高さには上下限を設け、急すぎる壁・穴・画面外への逸脱が発生しないよう平滑化する。
- 地形が生成される範囲と現在の入力に対する反応を、画面上で理解できるようにする。

### 3.2 声と地形の対応（初期案、定数は実装時に調整可能）
| 音声要素 | 地形への作用 | プレイヤーへの説明 |
|---|---|---|
| 声の高さ（pitch） | 自分の基準音より高い→上り坂、低い→下り坂、近い→おおむね平坦 | 「高く歌うと上る、低く歌うと下る」 |
| 声の大きさ（volume/RMS） | 声が大きいほど傾斜変化が強く、小さいほど緩やか | 「大きな声ほど大きく変わる」 |
| リズム（声の立ち上がり/onset） | 短く区切った発声を検出すると、前方の地形に小さな山・波を追加 | 「タン、タンと声を出すと波ができる」 |
| 無音・認識失敗 | 急変させず、徐々に平坦へ戻す | 「声を止めると平らになる」 |

詳細：
- pitchは声の個人差に対応するため、**初回の短い「あー」などから基準音の推定**ができるのが望ましい。初期版では基準音の再調整ボタンでもよい。
- 音量は環境雑音の影響を抑え、平滑化する。声の検出に失敗したフレームでは勝手に大きな坂を作らない。
- リズム判定は直前より急に強くなった発声を検出し、連続誤検知を防ぐクールダウンを設ける。
- 3要素の合成で極端な形にならないよう、最終地形の高さ・傾斜・変化速度を制限する。
- **自然言語の意味の解析やクラウドLLMはMVPでは不要。** Web Audio APIなどのブラウザ内処理を優先する。
- マイクの認識精度が難しい場合でも、まずはRMSと操作代替モードで遊べる作品を完成させる。pitch精度の改善は進捗に応じて行う。

### 3.3 操作
**マイクモード**：上表の音声入力で地形を変形。

**キーボードモード（必須、マイクなしで全機能を検証できる代替操作）**：
- ↑／↓：声が高い／低いことに相当する入力
- ←／→ または W／S：地形変化の強さ（音量相当）の増減（UIでも確認可能）
- Space：声のリズム入力（起伏を1つ追加）
- Esc：一時停止／再開

※キー割当は他のブラウザ操作との衝突があれば変更してよい。**マイクとキーボードは共通の地形生成ロジックに入力**する。

### 3.4 ステージ・スコア
- MVPは**固定された1ステージ**（約60秒）で十分。難易度や複数ステージは不要。
- 「音符」などの収集アイテムを高さが異なる位置に設置し、適切に地面を変形すると取れる。
- 障害物を設置する。ランナーが触れるとライフを1つ失い、短い無敵時間を設けて連続ダメージを防ぐ。
- 初期ライフ：3。ゴールまで到達したらクリア。ライフ0ならゲームオーバー。
- 収集アイテム：1個100点。ゴール到達：クリアボーナス300点（数値は調整可能）。
- ベストスコアはブラウザのlocalStorageに保存してよい（任意・優先度低）。
- ステージの障害物・アイテムは**初期の固定配置**でよい。マイクなしでもキーボードでクリアできる配置にする。
- 音声による地形操作の結果が攻略に影響すること。単なる音量に反応する背景アニメーションにならないようにする。

### 3.5 画面構成
1. **タイトル画面**：タイトル、ゲーム説明、操作モード選択、スタートボタン
2. **マイク準備画面**：権限許可・現在の入力状況・基準音の調整、マイク利用不可時の説明
3. **プレイ画面**：ランナー、現在・前方の地形、音符、障害物、スコア、ライフ、残り距離／時間、音声インジケーター（pitch/音量/リズム）
4. **ポーズ画面**：再開、タイトルへ戻る
5. **結果画面**：クリア／ゲームオーバー、得点、収集数、リトライ

演出は爽快感・分かりやすさを優先。初期は図形や簡易キャラクターでよく、有料素材不要。

## 4. 機能要件・優先順位

### P0：必須（この範囲が完成して初めてMVP完了）
- F01：タイトル→モード選択→プレイ→結果→リトライの画面遷移
- F02：自動横スクロールと、連続した地形の生成・描画
- F03：入力の変化が**これから生成される地形**に反映される仕組み
- F04：音量（RMS）、声の高さ（pitch）、声の立ち上がり（リズム）の取得または判定、および平滑化
- F05：キーボードによる代替入力（マイクを使わなくても最初から最後まで遊べる）
- F06：収集アイテム・障害物・ライフ・得点・クリア／ゲームオーバー
- F07：入力の状態と地形の変化が分かるHUD・チュートリアル表示
- F08：マイクの権限拒否・未接続・非対応時に安全にキーボードモードへ切替
- F09：ポーズ・再開・リトライ時のゲーム状態とマイク利用の適切な停止／再開
- F10：WindowsのChrome/Edgeで起動し、GitHubを通して2人が統合開発できる

### P1：余裕があれば
- 音と地形が連動する演出（光・波形・パーティクル）
- ステージの難易度や長さの選択
- ベストスコア記録
- チュートリアルの充実、マイク入力の再キャリブレーション
- 設定画面（音量感度、基準音、表示等）

### P2：今回の対象外
- 2人以上のリアルタイム対戦・オンライン協力
- ユーザー登録・ログイン・クラウドDB
- スマホ向けネイティブアプリ／アプリストア公開
- 音声のクラウド送信、生成AIによる会話・音声生成
- 無限の自動生成ステージ、オンラインランキング、課金、広告

## 5. 非機能要件・制約
- **追加費用0円**。有料API・課金必須サービス・有料素材・専用ハードウェアは使わない。
- **Windows×2台**で開発・動作確認できること。双方のWindows上のVS Codeを利用。
- **ブラウザで遊べる**こと。できれば無料の静的ホスティングでデモURLを公開する。
- フロントエンド完結を優先。サーバー、認証、DB、外部AI APIは必須にしない。
- マイク入力はブラウザ内で処理し、録音保存・外部送信しない。マイク利用中が分かり、画面終了・停止時には音声トラックを停止する。
- マイク取得はHTTPSまたはlocalhostなどの適切なセキュアコンテキストで実行する。
- 目標フレームレート：一般的なノートPC上でおおむね60fps、少なくともプレイに支障がない滑らかさ。正確なFPS保証は不要。
- ネットワークが一時的に切断されても、読み込み済みのプレイを継続できる構成が望ましい。
- READMEに導入、起動、操作、テスト、デプロイの方法を記載。
- 開発者の誰かのローカルPC固有の絶対パス、個人APIキー、会社の非公開データに依存しない。

## 6. 技術・アーキテクチャの希望（決定ではない）
- 言語候補：TypeScript
- 開発・ビルド候補：Vite
- ゲーム描画候補：Phaser、またはHTML Canvas／PixiJSなど
- マイク入力候補：Web Audio API（`getUserMedia` + `AnalyserNode`）
- pitch検出：ブラウザ内で使える軽量ライブラリ、または単純なピッチ推定器。必要精度・性能・ライセンスを確認して選定。
- バージョン管理：Git + GitHub、Pull Requestベース
- 公開先候補：GitHub Pages / Cloudflare Pages などの無料枠

**技術スタックの最終決定・ディレクトリ構成・モジュール設計・2人の役割分担・Herdr/Claude Code/Codexの使い分けは、Claude Codeに計画を提案させる。**

推奨する論理的な境界：`音声・手動入力の取得` → `共通の正規化された操作入力` → `地形生成` → `ゲーム進行・衝突・得点` → `画面描画`。同じ仕様の手動入力とマイク入力を入れ替えられるようにする。

## 7. 受け入れ条件（完成の判定）
1. Windows PC 2台でリポジトリを取得し、READMEどおりに起動できる。
2. キーボードだけでタイトルからゴールまたはゲームオーバーまで1プレイできる。
3. ↑/↓、強さ入力、リズム入力を変えると、予告された位置の地形が明確に変化する。
4. マイクの許可後、声の高さ・大きさ・区切りで地形の違いが観察できる（個人差により感度調整可能が望ましい）。
5. 無音時・入力が認識できないときに地形が暴れたり、アプリがクラッシュしたりしない。
6. 収集・障害物・ライフ・得点・クリア／ゲームオーバーが機能する。
7. ポーズ、リトライ、マイク利用停止を繰り返しても、重複ループやマイクトラックの残存がない。
8. マイクを拒否・未接続にしてもメッセージを表示し、手動モードで遊べる。
9. `npm run build` に相当する本番ビルドが通り、完成版を双方が確認できる。
10. GitHub上で2人が別ブランチの変更をPull Requestで統合した実績がある。

## 8. テスト観点
- **入力**：無音／小声／大声／高音／低音／連続した声／短く区切った声／雑音／マイク未接続
- **表示**：地形に段差や不自然な急変がない／HUDが変化する／アイテムとキャラの位置が一致する
- **進行**：60秒到達／障害物によるライフ減少／ライフ0／クリア／再挑戦／ポーズ
- **例外**：マイク許可拒否／プレイ中にタブが非表示／連続リトライ／画面サイズ変更
- **協業**：Gitのブランチ・PR・マージ・統合テスト、他人の変更の取り込み、衝突への対処

可能なら地形生成ロジックとスコア処理はマイクを使わない単体テストを書き、再現可能な固定入力で検証する。

## 9. 共同開発・AI利用の前提（役割分担は未定）
- 開発者：2人ともWindows + VS Codeを使用。
- 2人ともClaude Code、Codex、Herdrを利用する想定。**ただし、役割分担・設計をHerdr固有機能に依存させない。**
- 開発計画と仕事の配分は、まずるーは側のClaude Codeに提案してもらう。
- GitHubでブランチ／Pull Requestによる統合を練習する。`main`への直接コミットを原則避ける。
- 複数のAIや人間が**同一作業ツリー／同一ファイルを同時に無秩序に編集しない**。Claude Codeが具体的な作業境界と統合手順を設計する。
- 問題が起きたらログを確認し、事実と推測を分けて修正する。
- 会社の端末やAIを使う場合でも、勤務先の利用規則や機密保持に従う。今回の実装に業務上の非公開コード・データは持ち込まない。

## 11. 初期合意の優先順位
- 第一優先：**声／キー入力で目の前の地形が変わり、ランナーが走ってゴールできること**
- 第二優先：収集・障害物・スコアでゲームとして面白くすること
- 第三優先：演出、グラフィック、追加ルール

スケジュールが厳しい場合はP1/P2を切り、P0のうち高難度な部分（ピッチの精度など）の実装方式を簡略化してよい。ただし、音の高さ・大きさ・リズムというコンセプト自体を無断で削らず、削減案を提示して相談する。
